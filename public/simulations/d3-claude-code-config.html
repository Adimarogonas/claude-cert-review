Configuring Claude Code for a Team

Set up a shared repo: choose where conventions live, how rules are scoped, how a slash command is shipped, whether risky changes are planned first, how an unfamiliar-domain feature is approached, and how a reusable capability is packaged. Each choice deterministically moves the metrics on the right.

Repository configuration

A · Where do team conventions live?

Project-level CLAUDE.md is committed and loads for every contributor. ~/.claude/CLAUDE.md is user-scoped and never reaches teammates.

B · How are the conventions organized?

Path-scoped rules with paths: globs load only on matching files. A monolithic always-on file loads every rule on every edit.

C · How is the /review slash command shipped?

A committed .claude/commands/review.md is the right tool. User-scoped isn't shared; a full Skill is over-built for a fixed checklist.

D · The 45-file library migration is run…

Plan mode explores the deprecated client's usage before touching files. Direct execution on a risky multi-file change ships unreviewed edits.

E · A cache layer in an unfamiliar domain is built by…

The interview pattern lets Claude ask clarifying questions (invalidation, failure modes) and refine across passes. A single vague prompt loops unproductively and forces rework.

F · A reusable "summarize this PR" prompt is packaged as…

A simple repeatable prompt fits a committed .claude/commands/ slash command. Wrapping it in a full Skill (SKILL.md + bundled context) is over-built for a fixed prompt.

How this simulation works

  1. Make the six configuration choices (A–F) on the left.
  2. Press Run setup and watch the team metrics respond.
  3. Each choice writes a plain-English consequence to the log; red lines are the gotchas.
  4. Find the setup that maximizes adherence and propagation while keeping risky unreviewed changes and context cost low.
